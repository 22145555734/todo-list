## 2026-09-19

### 一、炫动色域随等级递增：1 级 ±5°/±8%，499 级 ±100°/±20%（PR #44）

#### 动机

原来 1~499 级的炫动幅度是**写死的** —— 色相左右各偏 ±8°、明度上下各偏 ±14%（`level.ts` 里 `SHIMMER_HUE_DEG` / `SHIMMER_LIGHT_PCT`）。用户要「幅度随等级变」：低等级只微微颤动，高等级颜色大幅流动，让「等级越高越炫」不止体现在**速度**上，也体现在**幅度**上。

#### 改动

- 把两个常量换成**端点常量**：`LV1_HUE_DEG=5` / `LV499_HUE_DEG=100`、`LV1_LIGHT_PCT=8` / `LV499_LIGHT_PCT=20`，中间按等级**线性插值**（与速度共用同一个进度 `t = (lv-1)/(MAX_LEVEL-2)`）
- `shimmerGradient` 从「读模块常量」改成「接收 `hueDeg` / `lightPct` 两个参数」，由 `levelShimmer` 算好传入
- 徽章底色与称号文字沿用**同一套幅度**（称号仍是 0.72 加深版，只是底色更暗，幅度不变）—— 没有给称号单独调，保持既有「两者共享常量」的行为

插值结果（两端点）：

| 等级 | 色相偏移 | 明度偏移 |
|---|---|---|
| 1 | ±5° | ±8% |
| 250 | ±52.5° | ±14% |
| 499 | ±100° | ±20% |

499 级深红 `hsl(0, 74%, 42%)` 偏移 ±100° 后，色相扫过 **260°（蓝紫）→ 0°（红）→ 100°（绿）**，共 200°；1 级绿只扫过 **137° → 147°**，共 10°。

#### 验证

- `npm test` **31/31 通过**（新增一条测试，断言 1 级与 499 级的单侧色相/明度偏移命中端点值，且 250 级严格夹在中间）
- `npm run build` 通过；JS 哈希随之更新（`index-Bo4ke-g2.js` → `index-DN6pV_AH.js`），CSS 哈希未变（`index.css` 只改了注释，编译产物不含注释）
- 生成各等级炫动色条预览图（桌面 `炫动色域预览.png`），逐像素采样复核：1 级色相跨度 10°、250 级 105°、499 级 200°，与插值公式一致

#### 部署

- PR #44 以 merge commit 合入（`96b5b1e`）
- 前端部署：清空远程 `dist` → 上传 → **24/24 md5 逐条一致** → `docker compose up -d --build --force-recreate frontend`；回滚点是上一版 `803cd4c08e42`，新版 `todo-app:latest` = `181146729872`

### 二、炫动幅度收窄到 ±70°/±13%，资深~首席段再减 20°/5%，等级进度条也加炫动

#### 动机

第一期（同一天）把幅度改成随等级递增，499 级给到 ±100°/±20%。**用户看过线上效果后反馈「好难看」** —— 499 级色相扫过 200°，整条渐变糊成一片彩虹，反而看不出是「本等级的颜色」；明度跨 40% 也让深色段过暗。同时用户要求：**等级进度条也要跟着炫动**（此前是纯色填充）。

#### 改动

- **端点收窄**：`LV499_HUE_DEG` 100 → **70**，`LV499_LIGHT_PCT` 20 → **13**。1 级端点 ±5°/±8% 不动，中间仍按 `t = (lv-1)/498` 线性插值
- **进度条加炫动**：`TodoList.tsx` 里进度条填充从 `background: levelColor(level)`（纯色）改为与徽章**完全同一套** —— 同一个 `shimmer.badgeImage`、同一个 `shimmer.durationS`，满级仍走 `.rainbow-bg`
- **资深 / 顾问 / 首席三档（251~400 级）再收一档**：在插值结果上额外减 `TRIM_HUE_DEG=20` / `TRIM_LIGHT_PCT=5`。用户原话「所有包含从资深到首席的对应等级，°都减去20°，明暗都减5%」—— 这三档正好覆盖 251~400，是 `RANKS` 表里连续的三行，所以按等级区间实现，不按称号名查表
- 顺带清掉因此变成孤儿的 `badgeColor` 变量与 TodoList.tsx 的 `levelColor` 导入（`level.ts` 的导出自留，`level.test.ts` 仍在用）

收窄前后的对比（499 级）：

| | 色相跨度 | 明度跨度 |
|---|---|---|
| 上一版 | 200° | 40% |
| 本版 | **140°** | **26%** |

#### 为什么进度条不是「另配一套更淡的渐变」

用户的原话是「等级进度条**也**要相应炫动」——「相应」即同一个等级色。进度条与徽章在视觉上属于同一张卡片，如果各自跑不同相位/不同幅度的渐变，会看起来像两条互不相干的动画。所以直接复用 `badgeImage`，代价是两处必须同步改（这也是为什么渐变算在 `level.ts` 里、而不是各组件自己拼）。

#### 为什么收窄段的两端要渐入渐出

按字面实现（251~400 一律减 20°/5%）会在两处边界各留一个 **20° 的台阶**：250 级是 37.5°，251 级骤降到 17.6°；400 级 57.1°，401 级弹回 57.2°。20° 在色相上是一眼可辨的差异，玩家升级瞬间颜色会「跳」一下 —— 而整个炫动系统的其余部分（速度、幅度）都是逐级连续变化的，只有这里会突变。

所以加了一个权重 `trimWeight(lv)`，两端各留一段线性过渡，中段取满：

| 区间 | 权重 | 效果 |
|---|---|---|
| 250 及以下 / 401 及以上 | 0 | 完全不受影响 |
| 251~260 | 0 → 1 渐入 | 251 级几乎没减，260 级取满 |
| 260~390 | 1 | 完整的 -20°/-5% |
| 390~400 | 1 → 0 渐出 | 400 级回到不收窄 |

这个取舍**没有静默按字面实现**：先把「直接减会出现台阶」这件事连同两处边界的实际数值摆出来，让用户在「两端渐入渐出」与「直接减」之间选，用户选了前者。渐入段取 9 级、渐出段取 10 级，是让过渡分摊到约十级上——单级变化约 2°，与相邻等级的天然色差同量级，看不出是「特意做的过渡」。

#### 验证

- `npm test` **33/33 通过**
  - 新增 DOM 测试：种子 2 小时（Lv.8，进度 ≈0.69），断言进度条填充带 `shimmer-bg`、`animationDuration` 与 `backgroundImage` 与徽章**逐字相等**、且宽度仍是百分比
    - 这条相等断言有「空对空」的风险（jsdom 若丢弃渐变，两边都是 `""` 也会通过），所以另加了一条 `toContain("linear-gradient")` 兜底 —— 实测 jsdom 保留了渐变，不是空对空
  - 新增收窄段测试：把 `badgeImage` 里的 `hsl()` 停靠点反解回色相/明度，与线性基线对拍。中段（260/300/350/390）确认减满 20°/5%，段外（250/401/499）确认完全不受影响，两处边界（250↔251、400↔401）确认连续，渐入段确认在爬（251 几乎没减、255 减到一半附近、260 取满）
    - 容差取 **0.5°** 而非更紧：`hsl()` 只序列化到 1 位小数，两个停靠点相减后回读有约 0.1° 的量化误差。第一版取 0.05 导致 `cut(251)` 断言失败（实测 -0.069°，纯属量化噪声）
- `npm run build` 通过；JS 哈希随之更新（`index-DN6pV_AH.js` → `index-BYjVpO7L.js` → `index-B1P6RHv2.js`）
- 生成预览图（桌面 `炫动色域预览3.png`：上半是幅度-等级曲线，把凹坑与两端过渡直接画出来；下半是各等级色条 + 四张等级卡片示意），**逐像素采样**复核：13 个采样级的色相跨度与公式最大差 0.64°（8bit RGB 量化），250→251 首端差 0.93°、400→401 差 0.24°
  - 采样器本身踩过一次坑：色条是 `lo→mid→hi→mid→lo` 五站跨满宽，mid 在 `px=(w-1)/4` 处。第一版取 `w//3`，落到 f≈1.33 的位置，量出来一律偏大约 1.33 倍（17 个点全「不符」）—— 是采样点错了，不是图错了

#### 部署

**尚未部署。** 视觉改动按惯例停在 PR（#46），等看完预览图再合并部署 —— 这一期本身就是上一期「没先看预览就上线」的直接产物。

#### 验证边界

- **没有在真机上看过效果。** 幅度、连续性、与公式的一致性都是靠单元测试 + 预览图逐像素采样确认的；「±70°/±13% 到底好不好看」「收窄段是不是真的更稳重」这类判断只能由用户看线上效果给出 —— 上一期正是栽在这一步

### 二、「子集」更名为「子任务」，子任务列表可收起（PR #17 · `f15f3f7`）

#### 动机

两件事一起做：

1. **「子集」这个词不好懂。** 界面上「合集」「子集」并列，都是集合论的词，但用户心里想的就是「这个任务下面还有几个小任务」。「子任务」是直觉词。
2. **子任务多了会把列表撑长。** 四门课还好，再多几门就得一直往下滚，需要一个收起来的开关。

#### 改动

**更名**：全仓库「子集」→「子任务」，11 个文件。

| 层 | 涉及 |
|---|---|
| 界面 | `TodoList.tsx` / `Stats.tsx` 的按钮、占位符、提示语 |
| 后端 | 报错消息（`子集下不能再加子集` 等，用户看得到） |
| 测试 | 与界面文案耦合的断言 |
| 注释 / 文档 | `src/` 各处注释、`README.md` |

`更新日志.md` 里 2026-09-17（PR #10）那条的「子集」**保持原样** —— 那是当时的记录，改写会让人以为功能当时就叫这个名字。更名这件事记在本期。

**收起 / 展开**：合集行右侧、`+ 子任务` 旁边加一个切换按钮。

| 决策 | 取值 | 理由 |
|---|---|---|
| 默认状态 | **展开** | 加子任务本就是为了给它们计时，点开就能点；折叠是主动收拾长列表的手段，不该是默认门槛 |
| 按钮位置 | 合集那一行，**不是**列表末尾 | 痛点就是列表长 —— 按钮得在不用滚动就能看到的地方 |
| 收起时点「+ 子任务」 | 自动展开 | 否则刚加的子任务看不见，等于操作没反馈 |
| 状态存放 | 内存，不持久化 | 纯视图偏好；刷新回到展开，与默认一致 |

收起后「N 个子任务」计数仍在计时行显示，用户依然知道里面有几个；正在计时的子任务也不会「消失」—— 计时行的「正在计时：X」照旧。

> 更名顺带撞出一处措辞重叠：统计页原有的「合并子集 / 展开子集」变成「合并子任务 / 展开子任务」，与列表的「展开」字面撞车。两者含义不同（一个是聚合维度，一个是折叠），且各在各自页面内，本次未另作区分。

#### 验证

- `npm test` **20/20 通过**（原 18，新增 2 条：默认展开且可收起 / 收起时点「+ 子任务」自动展开）
- `npm run build` 通过（tsc + vite）
- Tailwind 内核自检：`@layer` / `@property` / `oklch(` / `color-mix(` 均为 **0**，v3 约束未被破坏
- 全仓库旧词零残留（`更新日志.md` 的历史条目按上文说明保留）
- 后端只动了报错文案与注释，**接口契约未变**
- **未做浏览器实测**：`TodoList` 需登录后才渲染，本地无后端，交互由测试覆盖

#### 部署结果：后端这一半**漏了将近两天**，2026-09-18 23:22 才补上

期二的前端部分当天随构建上了线，**后端部分一直没部署**。而更名里恰恰有三处是用户看得到的报错文案：

| 报错 | 触发场景 |
|---|---|
| `合集请分别给子集计时` | 给合集本身点开始计时 |
| `目标事项不是该合集的子集` | 迁移时长时选错了目标 |

于是这段时间线上是割裂的：界面写「子任务」，报错还写「子集」。

**怎么发现的**：本轮合并 PR #40 时打算走一遍部署，先确认「线上跑的到底是哪一版」，顺手比对了后端镜像的构建时间（09-17 23:42）与最后一次后端提交的时间（09-18 13:41）—— 镜像更早。**没有停在时间戳推断上**，把镜像里的 `app.jar` 取出来解出 class 验了一遍：

### 三、展开 / 收起加过渡动画（PR #18 · `a048d36`）

#### 动机

PR #17 给合集加了「展开 / 收起」开关，但收起、展开都是瞬间切换——子任务列表直接挂载 / 卸载，按钮也只是纯文字，看着生硬。

#### 改动

**按钮加箭头**：文字「展开 / 收起」旁加一个 chevron 图标，收起时指右、展开时指下，`transition-transform` 旋转过渡。

**子任务列表加高度动画**：新增 `Collapsible` 组件，用 JS 测量内容自然高度（`scrollHeight`）驱动 `height` 过渡——展开从 0 平滑展开，收起平滑缩回 0。

| 决策 | 取值 | 理由 |
|---|---|---|
| 动画实现 | JS 测 `scrollHeight` + `height` transition | 纯 CSS 的 `grid-template-rows: 0fr/1fr` 需 Chrome 107，T7 内核 97 不支持；`max-height` 收起有「前段不动」的延迟感 |
| 收起后的内容 | 动画结束**卸载**，不是 `visibility: hidden` | 隐藏但留在 DOM 的元素仍可被键盘 Tab 聚焦 |
| 动画结束判定 | `transitionend` + 300ms `setTimeout` 兜底 | jsdom 不触发 `transitionend`，测试靠兜底定时器 |

### 五、满级炫彩动画首尾帧相连（PR #21）

#### 动机

满级（500 级）炫彩的彩虹流动动画循环到结尾会「跳」一下——`background-size:400%` 配 `background-position:0%→100%` 只位移了 3/4 个渐变周期，首尾帧图案对不上。

#### 改动

`index.css` 的 `.rainbow-bg` / `.rainbow-text` 把 `background-size` 由 `400%` 改为 `200%`，`@keyframes rainbow-shift` 终点由 `background-position:100%` 改为 `200%`。

关键在周期对齐：渐变首尾同色（`#ef4444`），图案周期 = `background-size`（一个 200% 背景宽）。百分比定位的位移是 `position × (容器宽 − 背景宽)`，终点 `200%` 对应位移恰好 2 倍容器宽 = 一个完整周期，于是 `0%` 帧与 `100%` 帧图案完全相同，循环无缝。原来 `400%` + `100%` 只位移 3 倍容器宽，落在周期的 3/4 处，跳变就出在这里。

| 决策 | 取值 | 理由 |
|---|---|---|
| 周期尺寸 | `200%`（原 `400%`） | 让「位移一个周期」对应的 position 是整数 `200%`，而不是 `400%` 下的 `133.33%` 魔数 |
| 终点方向 | `0% → 200%` | 与原来 `0% → 100%` 同向（背景向左流），只改位移量不改方向 |

#### 验证

- `npm test` **23/23 通过**（本次纯 CSS 改动，测试数不变）
- `npm run build` 通过，CSS 17.63 kB；产物中 `.rainbow-bg` / `.rainbow-text` / `@keyframes rainbow-shift` 均在

### 十、满级换云峰飞云体、泰斗换马善政毛笔楷书（PR #26、#27）

#### 动机

上一期给称号分了档：51~400 用霞鹜文楷、401~500 用得意黑。实际看下来两处都不对：

1. **得意黑不适合满级。** 它本质是一款**窄体**，字形天生瘦长、笔画细。用在「登峰造极」这种要撑场面的最高档上，恰恰是最没分量的一个。反馈原话：「瘦长瘦的，而且字体也不帅，不霸气」。
2. **泰斗与登峰造极该分开。** 401~499 是「次高」、500 是「最高」，共用一套字体等于把最后一档的独特性抹平了。

方向：换成**毛笔书法类**的粗壮字体。

#### 关键约束：这个字体品类的授权与体积互相打架

毛笔书法字体是本项目的**特殊品类**，有三条限制同时成立：

| 限制 | 说明 |
|---|---|
| **必须自托管** | Android 只带思源黑体，`font-family` 调不到任何书法字体（上一期已确认） |
| **天然很大** | 笔锋需要大量轮廓控制点。同为 6763 字，几何标题体约 1 MB，毛笔体 **3 MB 起步**，江湖体可到 25 MB |
| **多数禁止修改** | 「不允许修改，任何人不得修改或制作衍生版本」—— 而**子集化正是制作衍生版本** |

第三条是死结。上一期那两个字之所以只有 15 KB，是因为 OFL 明确允许子集化；而免费商用的书法字体绝大多数是**作者声明**授权，白纸黑字写着不许改。

调研过并排除的（连同原因，避免以后重复调研）：

| 字体 | 排除原因 |
|---|---|
| 温州鹿城瓯韵体 / 云峰游戏标题简体 / 站酷仓耳渔阳体 | 授权**禁止嵌入**（网页 / APP），正是本用法 |
| 优设书华体 | **付费**（个人商用 ¥69 / 企业 ¥199） |
| 李旭科书法 / 禹卫书法行书 / 叶根友系列 | 授权不明，商用通常需单独授权 |
| 平方塞北体 / 刘昂乐天体 / 赖江湖各体 / 飞波正点体 / 阿里妈妈东方大楷等 | 允许嵌入，但**明文禁止修改**，无法子集化；整包引入则最小 3.08 MB（塞北体），最大 25.94 MB（赖江湖飞扬体） |

**决策**：接受「**整包引入、不做任何修改**」。这样不触碰「禁止修改」条款，只需单独处理体积。

**删除得意黑**：`smiley-subset.woff2` 与 `OFL-SmileySans.txt` 因本次改动成为孤儿，一并移除。

```ts

```

| 档位 | 等级 | 字体 |
|---|---|---|
| 新手 | 1~50 | 页面默认 |
| 学徒 ~ 首席 | 51~400 | 霞鹜文楷（8.80 kB） |

| 登峰造极 | 500 | 云峰飞云体（7.56 MB） |

**7.56 MB 怎么消化**

直接发给每个访客不可接受。两条措施：

1. **按需下载。** `@font-face` 本身不预取字体，浏览器只在**真有元素用到该字体族**时才下载。云峰飞云体只出现在 500 级的称号与徽章上，故 1~499 级用户**一次都不会触发**这笔流量。
2. **nginx gzip**（`nginx.conf`）。只压传输、不动文件：磁盘上的 `.ttf` 与上游原文件字节一致。**线上实测 7,928,508 B → 5,001,907 B**（压缩率 63%）。`gzip_types` 刻意不含 `woff2`——那已是压缩格式，列进去白费 CPU。

两项合起来：受影响范围从「所有访客」缩到「满级用户」，单次体积从 7.56 MB 降到 5.00 MB；配合 `/assets/` 既有的 `immutable` 缓存头，每人只下一次。

**让 gzip 真正生效，踩了两个坑（都不报错，只是静默失效）**

1. **`gzip_types` 按响应头的 `Content-Type` 匹配，而 nginx 自带的 `mime.types` 里没有 `.ttf` 条目。** 不显式指定的话 `.ttf` 落到 `default_type`（`application/octet-stream`），于是 `gzip_types` 里写的 `font/ttf` 永远匹配不上，压缩**静默不生效** —— 部署后第一次 `curl` 复验，加不加 `Accept-Encoding: gzip` 都是 7,928,508 B。修法是给 `/assets/*.ttf` 单独一条正则 location 用 `default_type font/ttf` 纠正（正则 location 优先于前缀 location，故缓存头要重复一次）。顺带把字体类型也标对了，对浏览器更正确。
2. **部署脚本 `ssh-todo.sh --put <目录> <远程目录>` 是把「目录本身」解到远程目录下**，不是把目录内容摊进去。上传 `dist` 恰好符合直觉（落到 `/root/todo/dist`），于是上传 `nginx.conf` 时我照抄了同一写法，结果落到 `/root/todo/nginxstage/nginx.conf`，而 `/root/todo/nginx.conf` **始终没被替换** —— 容器重建了、配置却还是旧的，看起来一切正常。第二次复验才发现。以后传单文件要显式 `mv` 就位，并**用 md5 核对远端文件**，别只看「命令没报错」。

#### 遗留的授权边界（如实记录）

云峰飞云体采用「作者声明」授权，随包的 `字体授权说明.txt` 只写了「个人和企业都可免费商用」，并指向猫啃网的介绍页；**「网页嵌入」这一项是猫啃网授权表列为"可以"，属于第三方整理、页面自注"仅供参考"，并非作者的明文条款**。

- 镜像：`153b8a20…` → `7c3053fa…`，旧的那层成了悬空镜像（回滚点）。各版独有的仍只有 `dist` 那一个 COPY 层

| 新 | **1** | 只剩 `` `${O.titleSize}px`,…O.titleFamily?{fontFamily:…} `` |

徽章那一行整个消失了。这比「测试是绿的」更进一步 —— 绿的是源码，这里是**线上正在跑的字节**。

#### 又一次 CRLF 假警报：`nginx.conf`

准备上传时发现服务器 `nginx.conf` 的 md5（`714ae387`）和仓库（`4cd9e723`）对不上，像配置漂移。拉下来逐行 diff：**57 行全部报告「不同」，内容却一模一样** —— 服务器那份是 CRLF，我比对前只给本地做了 `tr -d '\r'`。

这与 9-15 那次 `docker-compose.yml` 是**同一个坑，隔三天又踩一次**。教训：**跨机器比 md5 前，两边都要归一化行尾**，否则任何文本文件都会常年「漂移」。`core.autocrlf=true` 让工作区是 CRLF、仓库里是 LF，服务器上那份又取决于当初怎么传的 —— 三方各说各话。

（顺带：`docker-compose.yml` 这次 md5 完全一致，因为上次上传用的是 LF 版。所以「服务器上是 CRLF」并非必然，取决于上传时本地工作区的状态。）

#### 另一个可复用的观察：`Stats-*.js` 换了名字，代码没换

`Stats-DGa5pA6O.js` → `Stats-CaUJ6zOE.js`，大小一模一样（10,056 B）。把线上那份旧的拉下来 diff 新产物，**唯一差异是它 import 入口 chunk 的那行路径**（`./index-D6PGEnpg.js` → `./index-mEGqzn8y.js`），自身代码逐字节相同 —— Rollup 的 chunk 哈希会吸收依赖 chunk 的哈希。

**「文件名变了」不等于「这段代码变了」，别拿文件名当变更范围的证据。**

### 十三、称号字体一档一款，学徒到泰斗各换一款（PR #35 · `f7fdaa6`）

**动机**（用户提出）：上一期之后，51~400 级仍然共用霞鹜文楷一款字体 —— 八档里只有三档看得出区别。用户要求**每档各用一款不同字体**，越往上越帅，但不要毛笔味太重的那种。

#### 选型：从 140 款里挑，逐档点名

候选池取自**中文网字计划**（`@chinese-fonts/*`，84 个包 / 140 款），按字形气质分四类出了 104 款备选图（楷 / 宋明 / 黑圆方 / 手写艺术）供用户逐档点名。最终：

| 档 | 等级 | 字体 | 引入方式 | 大小 |
|---|---|---|---|---|
| 学徒 | 51–100 | MapleMono-CN Regular（等宽黑） | 原样分片 ×2 | 47.2 KB |
| 研习者 | 101–150 | 霞鹜文楷 Regular | 原样分片 ×2 | 40.5 KB |
| 实践者 | 151–200 | 思源黑体 粗 | **自子集化** | 1.7 KB |
| 能手 | 201–250 | 江西拙楷 | 原样分片 ×2 | 39.6 KB |
| 资深 | 251–300 | 程荣光刻楷 | 原样分片 ×2 | 47.0 KB |
| 顾问 | 301–350 | 瑞美加张清平硬笔行书 | 原样分片 ×2 | 55.7 KB |
| 首席 | 351–400 | 鸿雷行书简体 | 原样分片 ×2 | 58.1 KB |
| 泰斗 | 401–499 | 志莽行书（钟齐） | 原样分片 ×2 | 73.8 KB |
| 登峰造极 | 500 | 云峰飞云体 | 整包 | 7.56 MB（未改） |

新手（1–50）仍走页面默认字体；徽章「Lv.N」仍一律走默认字体（上一期的结论不变）。

**怎么在不下整包的前提下看 140 款字体**：中文网字计划把每款切成 130~400 片 woff2，jsdelivr 能单片取。逐片读 cmap 建「字符 → 分片」映射，渲染时逐字挑覆盖它的那一片 —— PIL 没有 `unicode-range` 概念，只能自己查表。同一母体的各分片度量一致，逐字换字体不会错位。15 个目标字通常只落在 9~15 片里，140 款全下也只 **42.1 MB**，而不是几十 GB。

选型阶段另有两个坑值得记：

- **「这字没渲染出来」多半是字面率差异，不是缺字。** 同一字号下得意黑撑满字身框、千图笔锋手写体只有一半高，拼在一张图上就像后者没画。按 `getbbox()` 的墨迹高度线性归一到同一视觉大小后即正常 —— 一度按「渲染 bug」排查了三轮，方向是错的。
- **cmap 里有码位 ≠ 有真字形。** 用私用区码位（U+E000 起）渲一张「空模板」，把每个目标字的位图与它逐像素比对，才查出「平方萌萌哒」「qiji-fallback」这类字体里一堆字其实指向 `.notdef`。据此剔掉 4 款占位字字体。

#### 引入方式由授权决定，不是由体积决定

104 款候选里，能按 OFL 自由子集化的只是一部分。最终点名的九款分两类处理：

**其一，四款非 OFL 字体不走子集化。** 江西拙楷 / 程荣光刻楷 / 鸿雷行书简体 / 瑞美加张清平硬笔行书都是「作者声明免费商用」，其中程荣光刻楷与鸿雷行书简体的公开条款**明文写着「不可修改字体及制作衍生版本」**，另两款（江西拙楷、瑞美加）只说了可商用、**没有**授予修改权 —— 未授予即不可推定。而**子集化就是修改**（删字形、改 cmap）。

于是改为：**原样搬运中文网字计划已经切好的 woff2 分片，一个字节都不改**，只取覆盖本档那两三个字的那一两片，按 `unicode-range` 引用。分片是该计划发布给浏览器用的形态，原样引用不属于我方对字体的修改。这比「整包引入」的再分发量还小一到两个数量级。

**其二，实践者（思源黑体粗）自己子集化。** 它是 OFL，且中文网字计划里没有这一款（该计划无思源黑体），故取 Noto Sans SC Bold 整包用 fontTools 子集到「实践者」三字，1.7 KB。

代价是**同目录下并存两种机制**。没有强行统一成一种：非 OFL 那四款若也整包引入，就是 3~25 MB × 4；若也子集化，就越过了授权红线。机制的分裂是授权本身的分裂，写在了 `index.css` 顶部注释里。

> 一度考虑把三款 OFL 字体（MapleMono / 霞鹜文楷 / 志莽行书）也改成自子集化，能省约 200 KB。查了 MapleMono-CN 的发行包是 **134 MB**（含全 CJK），为几十 KB 去下它不划算，遂放弃 —— **最终统一为「中文网字计划有的就原样搬分片，没有的才自子集化」**。

| 位置 | 改动 |
|---|---|
| `frontend/src/level.ts` | `Rank` 新增 `font` 字段，八档字体族**并入 `RANKS` 表**；`levelFont()` 由写死档位判断改为查 `rankOf()`；删掉 `FONT_KAI` / `FONT_TAIDOU` / `FONT_PEAK` 三条常量 |

### 十五、每一级都有自己的色域炫动，速度随等级递增；满级提速 1.5 倍（PR #38）

#### 动机

用户提出：「500 级速度再快 1.5 倍，1 级是完全不动，每一级都要颜色略微向右炫动，但保持在自己的色域附近，等级愈高，炫动速度越快，但 499 应该是新 500 级速度的 0.8 倍，1 级是完全不动，逐级增加到 499」。

此前**只有满级**在动（整条彩虹），1~499 级全是静止纯色 —— 500 级和 499 级之间没有任何过渡感。

#### 速度：一条直线，两端按用户给的比例钉死

速度以「每秒跑完几个渐变周期」计，三个锚点直接来自用户：

| 锚点 | 速度 | 周期 | 依据 |
|---|---|---|---|
| 1 级 | 0 | 不动 | 「1 级是完全不动」 |
| 499 级 | 1.2 周期/秒 | **0.83s** | 新 500 级速度 × 0.8 |
| 500 级 | 1.5 周期/秒 | **0.67s** | 原来 1 周期/秒（`.rainbow-*` 的 `1s`）× 1.5 |

2~498 级在 0 与 1.2 之间**按等级线性插值**，即 `速度(lv) = (lv-1)/498 × 1.2`：

| 等级 | 周期 | 等级 | 周期 |
|---|---|---|---|
| 1 | 不动 | 250 | 1.67s |
| 2 | 415.00s | 300 | 1.39s |
| 50 | 8.47s | 400 | 1.04s |
| 100 | 4.19s | 499 | 0.83s |
| 167 | 2.50s | 500 | 0.67s（整条彩虹） |

**低等级实际等于不动。** 2 级的周期是 415 秒，10 级 46 秒 —— 这是「速度线性」的必然结果（速度 ∝ lv-1，周期就是它的倒数），不是 bug。真正看得出流动是 50 级往后。若想让低等级也动起来，改的是**插值方式**（比如对速度取对数），不是调端点。

**499 → 500 有一处速度跳变**（0.83s → 0.67s）：这是用户点名的比例（499 = 新 500 的 0.8 倍），故意留的台阶，不是插值断了。500 级同时换回**整条彩虹**——它不参与「本档色域」这条规则。

#### 幅度：色相 ±8°、明度 ±14%

「略微……保持在自己的色域附近」落成两个常数（`level.ts`）：

```ts
const SHIMMER_HUE_DEG = 8;    // 色相左右各偏这么多度
const SHIMMER_LIGHT_PCT = 14; // 明度上下各偏这么多个百分点
```

每级按自己的主题色生成 `linear-gradient(90deg, lo, mid, hi, mid, lo)` —— **首尾同色**，配合 `background-size: 200%` 与既有的 `rainbow-shift`（向右滚一个周期）形成无缝循环。称号那一条用的是**本色加深版**（`× 0.72`，同 `levelColorText`），否则在白底上对比度不够。

这两个数**是我选的默认值**，动图里同时给了另外两档备选（±4°/±7%「更轻」、±14°/±24%「更明显」），用户看完再定。

#### 改动

| 位置 | 改动 |
|---|---|
| `frontend/src/level.ts` | 新增 `levelShimmer()`、`toHsl()`、`hsl()`、`shimmerGradient()` 与 4 个常数；`levelRgb()` 被复用（仍然是私有） |
| `frontend/src/index.css` | `.rainbow-bg` / `.rainbow-text` 时长 `1s → 0.667s`；新增 `.shimmer-bg` / `.shimmer-text` |
| `frontend/src/TodoList.tsx` | 徽章与称号各多一条分支：满级走 `rainbow-*`，2~499 走 `shimmer-*` + 行内 `backgroundImage` / `animationDuration`，1 级保持原来的纯色 |
| `frontend/src/level.test.ts` | 新增 3 条（见下） |

**颜色只能写在行内**：每级色域不同，`background-image` 没法预先写进样式表。所以样式表里的 `.shimmer-*` 只管**形状**（`background-size`、`background-clip`、keyframes），颜色与时长走行内 —— `1s` 只是兜底默认值，实际每次都被行内 `animationDuration` 覆盖。

`hsl()` 用**逗号写法**（`hsl(143.0, 70.4%, 45.1%)`），不用空格分隔或 `oklch()` —— T7 内核（Chromium 97）只认老写法，这与「Tailwind 锁 v3」是同一条约束。

### 十六、炫动速度重调：1 级从「完全不动」改为 20s 一圈，499 级改为 1.145s（PR #39）

本条目覆盖**同一次交付里的连续两轮**调整。两轮都落在 PR #39 里，第一轮那个中间状态**从未上线**，所以合成一条记。

#### 动机

第一轮，用户提出：「登峰造极变成速度原来的 0.8 倍，499 变成现在的 0.7 倍，对应的所有等级都修改」。

第二轮紧接着，改的还是同一处：「1 级改成 20 秒，499 改成 1.145 秒，中间的等级都对应更改」。

**只动速度，幅度仍是上一期那两个默认值**（色相 ±8°、明度 ±14%），用户还没定夺。

#### 第一轮的「原来的」歧义，以及为什么那么解

「登峰造极变成速度**原来的** 0.8 倍」有两种读法：

| 读法 | 结果 | 是否自洽 |
|---|---|---|
| 第十期以来的 1.0 周期/秒 × 0.8 | 0.8 周期/秒（1.25s） | ✗ 比 499 级的 0.84 **还慢**，与「等级愈高，炫动速度越快」直接矛盾 |
| 上期跑着的 **1.5** × 0.8 | **1.2 周期/秒**（0.833s） | ✓ 仍是全线最快，499 那句的「现在的」也正好指 1.2 |

取后者：「原来的」= 改动前正在跑的 1.5，与下一句「499 变成**现在的** 0.7 倍」是同一个参照点。第二个依据是硬约束 —— 满级慢于 499 级会让这条曲线自相矛盾。

这一轮算出 500 级 1.2 周期/秒（0.833s）、499 级 0.84（1.190s）。**500 级那个值留到了最后，499 级的在第二轮被替换掉了。**

#### 第二轮：端点改成「直接给秒数」，1 级不再静止

用户不再给倍数，而是**直接给周期**：1 级 20 秒、499 级 1.145 秒。

这一轮有个语义变化：**1 级此前是「完全不动」**（`levelShimmer(1)` 返回 `null`，走纯色分支），现在它也要动 —— 这一点单独问过用户并得到确认。于是 `null` 的含义收窄成「只有满级」：

| 等级 | 十五期 | 十六期第一轮 | **最终** |
|---|---|---|---|
| 1 | 不动（`null`） | 不动（`null`） | **20.000s**（0.05 圈/秒） |
| 499 | 0.83s | 1.19s | **1.145s**（≈0.8734 圈/秒） |
| 500 | 0.67s | 0.83s | 0.83s（未再变） |

#### 插值方式：速度线性，不是周期线性

用户给的是两个**周期**（秒），很容易顺手续成「周期线性递减」。但两者只在端点相同，中段能差到 5 倍：

| 等级 | 按速度线性（采用） | 按周期线性 |
|---|---|---|
| 100 | **4.68s** | 16.25s |
| 250 | **2.17s** | 10.57s |
| 400 | **1.41s** | 4.89s |

**这组对比摆给用户看过，用户选了速度线性** —— 它延续「等级愈高，炫动速度越快」的匀加速语义，也是既有算法的延续，改动最小。公式仍是 `v(lv) = v1 + (lv-1)/498 × (v499 - v1)`，时长取其倒数。

最终各档：

| 等级 | 周期 | 速度（圈/秒） | 等级 | 周期 | 速度 |

### 十七、给 admin 灌入 10 条称号示例数据（生产数据操作，**无代码改动**）

#### 动机

用户要求「给 admin 用户添加所有称号对应的示例」。称号的字体、颜色、字号、炫动全都按等级算，要看全 10 档的实际效果，只能让账号里真的存在 10 个不同等级的待办。

#### 为什么绕过 API 直接写库

等级依据的是**单个待办**的累计时长 —— `elapsedMs(todoId)` = 该待办自己的已完成会话 + 其子任务的会话（`store.tsx`）。后端只有「开始 / 暂停」这类接口，时长是 `Date.now()` 的差值，**造不出任意历史时长**。所以直接写 `todos` 与 `time_sessions` 两张表。

#### 数据

每档取**中点**：同一档内字号与颜色也随等级连续变（称号 10→36px），中点最能代表这一档的样子。登峰造极只有 500 一级，没有中点可挑。

| 新手 | 25 | 6.8 h | 资深 | 275 | 180.9 h |
| 学徒 | 75 | 26.6 h | 顾问 | 325 | 238.3 h |

#### 踩到的坑：中文被双重编码（**截至写下这段时，那 20 行仍是坏的**）

灌完用户就反馈「示例名字是乱码」。查下来问题在**导入路径**，不在数据本身：

- MySQL 官方镜像不设置 locale（容器里 `LC_CTYPE=POSIX`），`mysql` 客户端的 `default-character-set=auto` 据此猜成 **latin1**

同一张表里 user_id=4 那条待办的 hex 是 `E7A4BA…`（正常的「示例」），说明**应用写入完全没问题**，坏的只有我手工灌的这 10 条 `todos` + 10 条 `time_sessions`。

修法：按下面两行 `delete` 清掉，再用带 `--default-character-set=utf8mb4` 的命令重灌同一份 `seed.sql`（文件本身是正确的 UTF-8，错的只是导入时的解释方式）。

**第一次发现时没有当场修** —— 用户先要求查根因，改生产数据需要单独授权，所以停在那里等。这个边界本身是对的：查根因和改生产数据是两件事，前者不需要许可，后者需要。

- 修复前 `hex(text)` 是 `C3A7C2A7C2B0…`，修复后是 `E7A7B0…`（「称」的正确 UTF-8）
- 10 条 `todos` + 10 条 `time_sessions` 数量不变，用 utf8mb4 客户端读出来是「称号示例 · 新手」等正确中文

#### 怎么清理

### 十八、两个分发产物：PWA（降级版）+ Electron 桌面外壳

用户要求「PWA 和 exe 各做一个，放到 GitHub Release 上」。两者都不是功能改动，是**让别人用得上**的两条路。

#### PWA 只能做成「降级版」，原因在 HTTPS

先说清楚代价，因为这不是取舍问题而是硬限制：

- **`navigator.serviceWorker` 在非安全上下文里根本不存在。** 站点是 `http://47.106.200.121:8310/`，公网 IP + 明文 HTTP 不构成安全上下文（只有 HTTPS、localhost、file:// 才是）
- Chrome 的「可安装」判定本身就要求 HTTPS。所以 Android Chrome 上「添加到主屏幕」**只会建一个带地址栏的普通书签**，不是独立 App

要变成真 PWA，得先有域名解析过来、开放 443、配 nginx TLS + 证书（Let's Encrypt 不给纯 IP 签证书）—— 那是动生产服务器的事。用户知情后选了**降级版：不动服务器**。

于是本轮做的是：`manifest.json` + 4 个图标 + `index.html` 的 head 标签。**没写 service worker** —— 写了也注册不上，那是死代码，等 HTTPS 到位再加。

iOS 的 `apple-mobile-web-app-capable` 走的是另一套机制（不依赖 HTTPS），所以 **iOS 上「添加到主屏幕」能真的独立窗口打开，Android 不能** —— 这个不对称是这次唯一实际拿到的收益。**未实测**：手边没有 iOS 设备。

#### 文件名是 `manifest.json`，不是 `.webmanifest`

惯例后缀是 `.webmanifest`，但它在这套部署里会被**当成 `application/octet-stream` 发出去，Chrome 直接拒收**。原因是 nginx 的 `mime.types` 里没有这个后缀 —— 实测线上 nginx/1.31.5，整个文件里只有一行 json：`application/json  json;`，`grep -i manifest` **零命中**。

这是「环境约束备忘」第 8 条（gzip 按 `Content-Type` 匹配）的同类坑：**产物对了、配置对了，栽在 MIME 上**。用 `.json` 则命中 nginx 自带的映射，且 Chrome 接受 `application/json`，**不需要改 nginx 配置** —— 代价为零，所以没有去加 `types` 块。

#### 四个图标各有各的规矩，不是一张图缩四遍

| 文件 | 画法 | 为什么 |
|---|---|---|
| `icon-192` / `icon-512` | 圆角方块，四角透明 | `purpose: any`，当普通图标用 |
| `icon-maskable-512` | **满幅**方块，图形缩进安全区 | Android 会自己套遮罩（圆形、方圆形…），图形超出安全区会被切掉 |
| `apple-touch-icon`（180） | **满幅**方块，图形比例稍大 | iOS 自己切圆角 —— 带透明角的会被它切出**黑边** |

配色取 App 自己的主色 `blue-500`（`#3b82f6`，登录按钮和主要按钮用的就是它），没有另起一套。对勾画好后在 24px 下仍认得出，这是选它的实际标准。

#### Electron 外壳：独立成 `desktop/`，不塞进 `frontend/`

`main.js` 里**没有任何应用逻辑** —— 窗口 `loadURL` 的就是线上站点，代码和数据都还在服务器上。它的全部价值是「双击即用」：不必记 IP 和端口，有自己的图标和窗口。

**`APP_URL` 是写死的**，所以换域名或上 HTTPS 都必须**重新打包发版**。这条要记住：站点地址和 exe 是绑在一起的两个产物。

独立成 `desktop/` 而不是加进 `frontend/`，是因为 `frontend/` 是**部署用的 Docker 构建上下文**，不该混进 electron 这类只在本地用的依赖。

#### 踩到的两个坑（都在构建环节，不在代码里）

**① `npm install` 直接崩，且报错读不出原因。** electron 的二进制不在 npm 上，是 postinstall 里从 GitHub Releases 拉的，国内直连被掐，进程以 `3221226505` 退出。解法是在 `desktop/.npmrc` 里落 npmmirror 镜像 —— 这两个键会变成 `npm_config_electron_mirror` / `npm_config_electron_builder_binaries_mirror`，正好是 electron 的 `install.js` 和 electron-builder 的 `binDownload.js` 要读的环境变量名。**验证方式：清空 electron 二进制缓存、不设任何环境变量、纯净 `npm install` 通过**（否则本地装过一次就永远测不出镜像到底有没有生效）。

**② electron-builder 解压 `winCodeSign` 失败。** 那个包里含 macOS 的 `.dylib` **符号链接**，而 Windows 上创建符号链接需要管理员权限或开发者模式，于是解压报「客户端没有所需的特权」并重试 4 次。绕过办法是手工解压、用 `-x!darwin` 跳过含符号链接的目录，再把它放到 electron-builder 期望的缓存位置 `winCodeSign-2.6.0`（数字名的那几个目录是解压失败后残留的临时目录，不是它要找的名字）。**`rcedit-x64.exe` 就在这个包里** —— 它正是给 exe 写图标和版本信息的工具，所以这个缓存不能省。

### 二、修复移动端样式全部失效：Tailwind v4 → v3（PR #5 · `03aac73`）

#### 现象

手机端**只显示最朴素的 UI，没有任何排版和样式**；PC 端正常。

#### 排查与根因

先确认**不是** CSS 请求失败。服务器 nginx 访问日志显示请求完整成功：

```
"GET /assets/index-CIgt4UZ3.css" 200 20619
"GET /assets/index-D33A21lE.js"  200 160289
```

CSS 以 **HTTP 200 / 20619 字节**完整送达，是**解析阶段被拒**而非请求被拦。

真正原因：**Tailwind v4 用原生级联层输出样式**。产物 CSS 结构：

```
CSS 总长 20619 字节
@layer properties  偏移     65

@layer base        偏移   3625
@layer utilities   偏移   7346  ← 一直到文件结尾
.mx-auto / .bg-white / .rounded-xl / .p-6 … 全部在 @layer utilities 内
```

`@layer utilities` 一段 **13273 字节，占整个样式表的 64%**。CSS 规范中浏览器遇到不认识的 at-rule 会**把整个块连同内部规则一起丢弃**，于是页面退化为无样式 HTML。

**触发条件是用户设备的内核版本。** 从日志取到实际 UA：

```
Linux; Android 16; PJZ110 … Chrome/97.0.4692.98 … T7/15.54 … baiduboxapp/15.55.0.10
```

一加13 / Android 16，但百度 App 用的是**自家 T7 内核 = Chromium 97**，而：

| 特性 | 需要版本 | Chromium 97 |
|---|---|---|
| `@layer` | Chrome **99** | ❌ 差 2 个版本 |
| `oklch()` / `color-mix()` | Chrome **111** | ❌ 差 14 个版本 |
| ESM（JS 能否执行） | Chrome 61 | ✅ 满足 |

这解释了「**页面有内容但完全没样式**」这个组合：JS 跑得了（所以有内容），CSS 被丢弃（所以没样式）。

**问题不在设备**——同一台手机的系统 WebView 是 Chromium 130+，用系统浏览器打开完全正常。是 App 自带内核滞后。

#### 改动

Tailwind **v4.3.3 → v3.4.17**（v3 输出纯 CSS，官方支持 Chrome 45+ / Safari 12+）：

- 卸载 `@tailwindcss/vite` + `tailwindcss@4`，安装 `tailwindcss@3.4` + `postcss` + `autoprefixer`

- `vite.config.ts` 移除 `tailwindcss()` 插件
- `src/index.css`：`@import "tailwindcss"` → `@tailwind base/components/utilities`

### 三、修复部署后移动端长期拿到旧版本（PR #6 · `c8aec99`）

#### 现象

上线第二期修复后，**夸克正常了，百度 App 仍然无样式**。

#### 排查与根因

同一份服务器文件、同一台手机，两个浏览器表现不同——这直接排除了代码问题，指向客户端。查日志，看部署后百度 App 的**全部**请求：

```
百度App  03:03:28  GET /api/todos      200 813
百度App  03:03:28  GET /api/sessions   200 794
百度App  03:05:15  GET /api/todos      200 813
百度App  03:05:15  GET /api/sessions   200 794
```

**没有一条 `GET /`，没有一条 `/assets/*`。** 对比夸克：

```
夸克  03:04:01  GET /                          200    396
夸克  03:04:01  GET /assets/index-M9EgBFvv.css 200  15116
夸克  03:04:01  GET /assets/index-01YtoMAf.js  200 160289
```

结论：**百度 App 把整个页面（HTML + CSS + JS）都缓存了**，跑的是缓存里的旧 Tailwind v4 CSS，第二期的修复**根本没送达**。API 返回 200 说明带着有效 JWT、JS 运行正常，只是样式是旧的。

根因在 nginx：

```
$ curl -sI http://47.106.200.121:8310/
HTTP/1.1 200 OK
Content-Type: text/html
Last-Modified: …
ETag: "6aab5784-18c"
                        ← 没有 Cache-Control
```

`nginx.conf` 未设置任何 `Cache-Control`，浏览器便自行套用启发式缓存，各家用多激进全凭自己：夸克还算克制会回源，百度 App 则长期不校验。

**用 `?v=2` 绕过缓存验证**（缓存按完整 URL 做键，新键必然未命中）：

```
03:09:31  GET /?v=2                        200    396
03:09:31  GET /assets/index-M9EgBFvv.css   200  15116   ← 新 CSS
03:09:31  GET /assets/index-01YtoMAf.js    200 160289   ← 新 JS
03:09:31  GET /favicon.ico                 200    396   ← 连图标都重取
```

`favicon.ico` 也被重新请求，是「真正全新加载」的铁指纹。至此缓存假设确认。

#### 改动

```nginx
# 构建产物（文件名含内容哈希，内容变则文件名变）：可永久缓存
location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
}

# 入口 HTML：每次回源校验（命中 ETag 返回 304，开销可忽略）
location / {
    try_files $uri $uri/ /index.html;
    add_header Cache-Control "no-cache";
}
```

标准 SPA 配法：**入口不缓存 + 哈希资源永久缓存**。`index.html` 仅 396 字节，每次 304 校验成本可忽略；带哈希的资源文件名随内容变，缓存永不冲突。

#### 验证

| 检查项 | 结果 |
|---|---|
| 入口 HTML `Cache-Control` | `no-cache` |
| 哈希资源 `Cache-Control` | `public, max-age=31536000, immutable` |
| 条件请求（`If-None-Match`） | **HTTP 304** |
| API 反代 | 401（正常，空 body 被拒） |

部署流程改进：替换线上配置前，先用共享网络的一次性容器跑 `nginx -t` 校验语法，通过后才替换。

### 四、待办事项支持合集 / 子集（PR #10）

#### 需求

一个待办事项可能是几个的合集，例如「408」包含 4 门课。人不可能同时在 408 和操作系统上分别计时，于是希望：

- 一个事项可以加若干**子集**，子集可以**独立计时**
- 子集**没有等级和荣誉系统**
- 子集时长之和 = 该事项的总时长，等级/荣誉按这个总时长算
- 有了子集的**事项自身取消计时功能**
- **不加子集的事项行为完全不变**

#### 数据模型

只加两个可空列，`ddl-auto: update` 会自动迁移（MySQL 8 的 `ADD COLUMN` 对可空列是 INSTANT 操作，不重建表）：

| 列 | 含义 |
|---|---|
| `todos.parent_id` | 所属合集 id；null 表示顶层事项。**只允许一层嵌套** |
| `time_sessions.root_subject` | 开计时时快照的合集名；null 表示不属于任何合集 |

`root_subject` 是必需的：计时记录**故意在待办被删后保留**（见下），统计因此无法反查待办表，只能在记录里快照一份合集名。

#### 关键设计

**1. 统计的合并 / 展开**

聚合键取 `rootSubject ?? subject`：

| 视图 | 聚合键 | 效果 |
|---|---|---|
| 合并（默认） | `rootSubject ?? subject` | 408 及其 4 门课合成一根柱子 |
| 展开 | `subject` | 4 门课各自成柱 |

没有子集时开关**不显示**，界面与改动前一致。层级聚合全部在**前端**完成（`time.ts` 的 `buildStats`），后端不新增任何计算。

**2. 删除语义：删事项，留记录**

`TimeSession` 的注释写着「删除待办后保留历史，用于统计」，这是原有约定。合集沿用同一条：**级联删掉子集事项与计时记录无关**——事项删了，计时记录仍然保留。

`clearCompleted` 需要特别处理：合集已完成时它的子集会被级联删除，遍历时必须跳过这些子集，否则会重复删除。

**3. 历史时间迁移**

给一个已经计过时的事项加第一个子集时，前端弹出提示，让用户把已有记录**手动迁到某个子集**（`POST /api/todos/{id}/adopt-time`），也可以选「暂不迁移」。迁移会改写记录的 `todoId` / `subject` / `rootSubject`。

**4. 单计时器规则不变**

`TimeSessionService.start()` 仍会自动关掉其它正在跑的计时器——**同一时刻只有一个计时器**。这条对子集同样生效，因此不能同时给「数据结构」和「操作系统」计时。后端额外拒绝给合集计时，并在创建子集时结束合集可能仍在跑的会话，保证「合集不存在运行中的会话」这个不变量。

#### 验证

- 后端 `mvn compile` 通过
- 前端构建通过
- 测试 **17/17** 通过（新增 4 条：合集自身无计时、子集无等级、删除级联、迁移提示）

## 环境约束备忘

1. **Tailwind 必须保持 v3，不要升级 v4。** 决定因素不是「新不新」而是**目标用户的浏览器内核**。百度 App 的 T7 内核为 Chromium 97，不支持 `@layer`。升级 v4 的前提是所有目标浏览器 ≥ Chrome 99。自检方法：构建后检查 `dist/assets/*.css` 中 `@layer` 计数，v4 会 > 0。

2. **部署后若用户反馈「还是旧版本」，先怀疑缓存。** 读 nginx 访问日志即可判定：若只有 `/api/*` 没有 `/assets/*`，就是缓存未刷新，让用户清一次缓存即可（`index.html` 现已为 `no-cache`，此为一次性操作）。

3. **排查移动端问题优先读访问日志，不要停留在推断。** 本次两次关键定位（内核版本、缓存未刷新）都来自日志中的 UA 与请求序列。日志里没有的结论，都只是假设。

4. `@vitejs/plugin-legacy` 只降级 JS，不处理 CSS，无法解决 `@layer` 这类问题。

5. **中文字体只能自托管，且「免费商用」≠「可用于网页」。** Android 只带思源黑体，`font-family` 调不到任何书法字体，所以换字体必须自托管文件。挑字体时按授权分三档看：

   | 档 | 协议 | 能做什么 |
   |---|---|---|
   | **OFL**（霞鹜文楷、马善政、得意黑等） | SIL Open Font License 1.1 | 可修改、**可子集化**、可嵌入、可再分发。最省心 |
   | **作者声明「免费商用」**（云峰飞云体、平方系列、庞门正道等） | 各家自定 | 通常**明文禁止修改** —— 于是**不能子集化**，只能整包引入；嵌入一项常有留白 |
   | **付费**（优设书华体等） | 商业授权 | 本项目不用 |

   实际影响：OFL 字体子集化后约 10 KB；不能改的毛笔体整包 3~25 MB。**给项目挑字体时，先确认授权是否允许修改，再谈好不好看** —— 顺序反了会白挑一轮。

6. **`ssh-todo.sh --put <目录> <远程目录>` 是把「目录本身」解到远程目录下**，不是把目录内容摊进去。传 `dist` 恰好符合直觉（落到 `<远程目录>/dist`），但**传单文件会落到 `<远程目录>/<本地目录名>/` 下面**，原文件不动。传单文件的正确姿势：上传到暂存目录 → 远端 `mv` 就位 → **`md5sum` 核对**。只看「命令没报错」会被骗过去 —— 容器照常重建、站点照常可访问，只有配置没变。

7. **用 `docker exec ... mysql` 灌含中文的数据，必须显式带 `--default-character-set=utf8mb4`，否则中文会双重编码。** 2026-09-18 给 admin 灌称号示例时踩到，页面上显示成 `ç§°å·ç¤ºä¾‹ Â· æ–°æ‰‹`。根因是一条链：

   - MySQL 官方镜像**不设置 locale** —— 容器里 `LANG` 为空、`LC_CTYPE=POSIX`
   - `mysql` 客户端的 `default-character-set` 默认值是 **`auto`**，含义是「按 OS locale 猜」
   - POSIX locale 下猜出来的结果是 **latin1**

   于是 UTF-8 的 SQL 文件被按 latin1 解释：字节 `E7 A7 B0`（「称」）读成 latin1 的 `ç§°`，再按 utf8mb4 存成 `C3A7 C2A7 C2B0` —— 每个字节各自升格成一个字符。这就是双重编码。

   **为什么应用没事**：后端走 JDBC（`characterEncoding=utf8`），链路里根本没有 locale 这一环。所以这类乱码**只会出在手工灌数据时**，不会出在应用写入的数据上（实测对照：同一张表里应用写入的中文 hex 是 `E7A4BA…`，正常）。

   **一个极具迷惑性的现象**：用 `docker exec mysql` 查回来**看着是正常中文**。因为显示路径上又做了一次方向相反的转换（utf8mb4 → latin1 输出 → 终端按 UTF-8 解释），两次错误恰好抵消。**唯一的硬证据是 `hex()`，不是肉眼看着对不对**：

   ```sql
   select hex(text) from todos where ...;
   -- 正常 UTF-8 中文以 E4~E9 开头；双重编码以 C3 开头（ç = C3A7）
   ```

   正确灌法（多一个参数就对了）：

   ```bash
   docker exec -i todo-mysql mysql --default-character-set=utf8mb4 -utodo -p"$MYSQL_PASSWORD" todo < seed.sql
   ```

   **修法用「删掉重灌」，不用 in-place UPDATE。** 2026-09-18 实修走的就是这条路，已验证：按第十七期那两行 `delete` 清掉，再用上面那条带 `--default-character-set=utf8mb4` 的命令重灌同一份 `seed.sql`。双重编码理论上可逆（每个源字节都落在 U+0000~U+00FF 内，`update ... set text = convert(binary convert(text using latin1) using utf8mb4)` 应该能转回来），**但这条 UPDATE 我没实测过**，所以没有采用 —— 坏数据只是示例，重灌比赌一条没验过的转换更直接。

   重灌前**核对种子文件的 md5**（本地 vs 服务器）。少了这一步，万一上传途中文件坏掉，修完还是乱码，会误判成「方法不对」再查一轮。

8. **gzip 不生效多半是 `Content-Type` 没对上，而不是 `gzip_types` 写错了。** `gzip_types` 按响应头的 `Content-Type` 匹配；nginx 自带 `mime.types` **没有 `.ttf` 条目**，`.ttf` 会落到 `default_type`（`application/octet-stream`）。验证方式：`curl -H 'Accept-Encoding: gzip' -o /dev/null -w '%{size_download}'` 对比加不加该头的大小，别只看配置里有没有写 `gzip on`。

9. **`desktop/` 的 Electron 打包在国内环境有两个固定故障点，都不在代码里。**（2026-09-18 首次打包 exe 时全踩到）

   - **`npm install` 崩在 electron 的 postinstall**，退出码 `3221226505`，报错信息读不出原因。electron 与 electron-builder 的二进制都不在 npm 上，是 postinstall 里从 **GitHub Releases** 拉的，国内直连被掐。`desktop/.npmrc` 里已落 npmmirror 镜像（那两个键恰好就是 electron 的 `install.js` 与 electron-builder 的 `binDownload.js` 要读的环境变量名），**照常 `npm install` 即可**。
     - ⚠️ 验证镜像有没有生效，必须**先清空 `%LOCALAPPDATA%\electron\Cache` 且不设任何环境变量** —— 本地装成功过一次之后，缓存会让后续任何配置都「看起来有效」。
   - **electron-builder 解压 `winCodeSign` 失败**：包里含 macOS 的 `.dylib` **符号链接**，Windows 建符号链接要管理员权限或开发者模式，于是报「客户端没有所需的特权」并重试 4 次后放弃。绕过：用包内的 `7za.exe` 手工解压并 `-x!darwin` 跳过符号链接，产物放到 electron-builder 期望的缓存位置 `%LOCALAPPDATA%\electron-builder\Cache\winCodeSign\winCodeSign-2.6.0\`。
     - 缓存目录名是 `<name>-<version>`，**别被一堆纯数字目录骗了** —— 那些是解压失败后残留的临时目录，electron-builder 不会去那里找。
     - **这个缓存不能省**：给 exe 写图标与版本信息的 `rcedit-x64.exe` 就在包里，缺了它只能打出没有图标、没有版本信息的 exe。

## 部署信息

- 地址：http://47.106.200.121:8310/
- 目录：`/root/todo/`
- 服务：`todo-mysql`（MySQL 8）、`todo-backend`（JRE 21）、`todo-app`（nginx，反代 `/api` → backend:8080）
- 端口：仅 8310 对外

服务器目录与仓库**同构**（2026-09-18 起）：

```
/root/todo/
├── frontend/{Dockerfile, nginx.conf, dist/}   # 前端构建上下文
├── backend/
├── docker-compose.yml                          # frontend 的 build.context = ./frontend
└── .env                                        # 只存在于服务器，绝不提交
```

**部署流程**：先清空远程 `frontend/dist`。上传是解包覆盖、只增不删，不清就会持续累积历次构建的哈希文件 —— 2026-09-18 一次性清掉 4 个共约 197 KB（`index-BMaBm_re.js`、`index-x0-7uTL0.css`、`Stats-CSlg7KrG.js`、`smiley-subset-Cg7bpxhD.woff2`）。此后固定为：

```
cd frontend && npm run build
→ rm -rf /root/todo/frontend/dist      # 先清空，见下
→ 上传 frontend/dist、frontend/nginx.conf、docker-compose.yml
→ 校验 nginx 语法
→ docker compose up -d --build --force-recreate frontend
```

**`docker-compose.yml` 必须一起上传** —— 这是整理目录时暴露的漏洞：此前部署流程从不上传它，服务器上那份从 9-15 起就没动过。当时核对下来只是行尾（CRLF vs LF）差异、内容一致，所以一直没出事；但只要仓库里真改了它（比如这次改 `build.context`），不上传就会「仓库改了、服务器没改」，下次构建直接挂。

清空是**安全的**：frontend 服务没挂 volume，`Dockerfile` 是 `COPY dist/`，线上容器读的是**镜像里自带的那份**，`/root/todo/frontend/dist` 只是构建原料 —— 动它不影响正在跑的站点，不存在「清空瞬间访客 404」的窗口（这一点 2026-09-18 之前我判断错了，当时以为有风险）。

上传后要比对一次文件清单 / md5（本地与远程 `dist` 应完全一致），否则上传中断会留下一份残缺的 dist，被下一次构建烤进镜像。比对本身有三个坑，2026-09-18 实跑时全踩到了：两边都要 `LC_ALL=C sort`，否则本地 locale 与远程字节序不同、排序不一致会**误报差异**（`Stats-*.js` 里的大写 `S` 就会错位）；比 md5 还要归一化 `md5sum` 的分隔符（本地 git-bash 是二进制模式 `hash *file`，远程是 `hash␣␣file`），否则 7 个文件哈希全同也会整片报差异；**比任何文本文件前两边都要去掉 `\r`** —— `core.autocrlf=true` 让工作区是 CRLF 而仓库里是 LF，服务器那份又取决于当初怎么传的，不归一化就会像配置漂移（`nginx.conf` 与 `docker-compose.yml` 各中过一次，见第十二期）。

（若哪天想手工核对哪些文件还在用：以 `dist/index.html` 为起点顺藤摸瓜 —— 入口 html 给出 js/css，入口 js 给出懒加载分块如 `Stats-*.js`，入口 css 给出版本化字体。）

**删这些文件不影响回滚。** 回滚靠的是 `docker images -f dangling=true` 里那批悬空镜像 —— `Dockerfile` 是 `COPY dist/`，每个镜像**自带**构建当时的一整套文件，不读 `/root/todo/frontend/dist`（已实测：上一个版本的镜像 `0c187792b9e9` 里仍完整保有它那一版的 `index-BMaBm_re.js`、`smiley-subset-Cg7bpxhD.woff2` 等）。所以只要不 `docker image prune`，任何一版都能直接 `docker run` 起来。

**镜像保留策略：只保留最近 3 个悬空镜像（= 前 3 个版本可回滚），更老的删掉。** frontend 与 backend 各自算一份；当前在跑的 `todo-app:latest` / `todo-backend:latest` 是 tagged 的，天然不在清理范围内。

- 做法：按 `com.docker.compose.project=todo` + `com.docker.compose.service` 过滤悬空镜像，按创建时间倒序保留最近 3 个，其余**逐个 `docker rmi <id>`，不加 `-f`** —— 被容器占用的镜像 Docker 会自己拒绝删除，这是安全网。
- **绝不使用 `docker image prune` / `docker system prune`**：那是全局命令，会牵连本机其它项目。这台服务器上还跑着 `redis1/2/3`（`redis:8.0-alpine`，已开机 15 个月）和 `mysql`，它们的镜像必须原样保留。
- **别按镜像标称大小估算收益。** frontend 镜像之间几乎全部层共享，各版独有的只有 `dist` 那一个 COPY 层。2026-09-18 首次执行：镜像数 30 → 14，删掉 16 个（0 失败），但 `docker system df` 里 Images 的 SIZE 几乎没动（1.443GB → 1.44GB），实际只释放约 3MB。**这条规则的价值是「回滚集有界、看着清爽」，不是省磁盘** —— 当时残留的 519MB 可回收空间主要来自未使用的**基础镜像**（`redis:latest` 128MB 等）与 build cache，与版本累积无关，且不属于本项目、未动。
